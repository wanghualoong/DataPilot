# ADR-0011：项目内核的并发模型

- 状态：已采纳（2026-11-09）
- 相关：ADR-0005（项目）、docs/12-projects.md「内核内的并发」

## 背景
一个项目的所有对话共用一个内核进程和一个 `data.duckdb`（DuckDB 只允许一个进程读写同一个库文件）。原来内核从 stdin 逐行读请求、逐个执行，问题有三个：
1. A 对话导入几百 MB 的 CSV 时，B 对话的简单查询和检查器刷新都要等它做完。
2. 请求超时或用户按「停止」都会重启整个内核，同项目其他对话正在做的事也被一起杀掉。
3. 检查器只能在内核忙时跳过刷新。

## 决策
**仍然是一个进程**：这是 DuckDB 的硬性约束，所以保留"一个项目一个内核"，改为在进程**内部**并发：
- **每个请求一个线程、一个 DuckDB 游标。** DuckDB 支持同一进程内多个游标并发读、并发写不同的表（乐观并发控制），执行查询时会释放 GIL。实测（DuckDB 2.0.0）：
  - 一个游标在跑长查询时，另一个游标的查询 0.001 s 返回；
  - 两个游标同时写不同的表正常完成；
  - `interrupt()` 0.5 s 内停下；
  - `register` 的临时表只对本游标可见。
- **同一对话内保持顺序**（每对话一个 FIFO 队列），和 Jupyter 一个 notebook 内顺序执行一致，保证"先导入再分析"的依赖。
- **`exec` 跨对话也串行**（全局锁）。原因：
  - matplotlib 的 pyplot 状态是进程级的，并发画图会混图或互相 `close("all")`；
  - 纯 Python 计算受 GIL 限制，并行收益很小。
  - 真正耗时、值得并行的通常是 SQL 和导入，这两类已放开。
- **取消只针对一个请求**：中断游标 + 向线程抛异常；10 s 宽限期内停不下来才重启内核。

## 与主流做法对比
| 系统 | 做法 |
|---|---|
| Jupyter | 一个 notebook 一个 kernel，kernel 内顺序执行；两个 notebook 连同一个 `.duckdb` 会锁冲突 |
| Databricks / Hex | 同一个 notebook 内顺序执行；不同用户 / notebook 在共享计算引擎上并发 |
| Claude Code / Codex | 只读工具并行，有副作用的工具串行 |
| DataPilot（本 ADR） | 同一对话顺序执行；不同对话的数据操作并发；Python 代码执行全局串行 |

## 代价与风险
- **卡在 C 代码里的 Python 无法立即取消**：比如 pandas 正在 `read_csv`。这种情况会等宽限期结束后退回重启内核，和原来的行为相同，但只在少数情况下发生。
- **`PyThreadState_SetAsyncExc` 的时机**：异步异常可能在请求刚完成时到达。完成时在锁内把状态置为 done 并清除挂起的异步异常，避免误伤下一个请求。
- **用户代码里的线程**：其输出写到 stderr，不进协议流。
